Chapter one · Foundations

01DevOps & MLOps foundations

Before any tool: DevOps is a culture that collapses the wall between the people who build software and the people who run it, so that change becomes fast, frequent and safe.

For decades, Dev (developers, who want change) and Ops (operations, who want stability) were separate teams with opposite incentives. Code was thrown "over the wall", releases were rare, risky, manual events, and when something broke each side blamed the other. DevOps is the answer: one shared culture, with automation removing the manual hand-offs so software can be released continuously and reliably. MLOps then takes those same ideas and stretches them to cover the extra moving parts of machine learning, namely data and models.

The concepts worth knowing cold

CALMSWillis / Humble, ~2010Core
The five-letter checklist for whether an organisation is "doing DevOps" for real.
  • C — Culture: shared responsibility, no blame, Dev and Ops as one team.
  • A — Automation: remove manual steps (builds, tests, deploys, infra).
  • L — Lean: small batches, reduce work-in-progress and waste.
  • M — Measurement: you cannot improve what you do not measure (see DORA).
  • S — Sharing: open knowledge, tools and feedback across teams.
The Three WaysKim et al., The Phoenix Project (2013)Core
The principles underneath every DevOps practice.
  • 1. Flow: speed work left-to-right (Dev to Ops to customer). Small batches, automation, no bottlenecks.
  • 2. Feedback: amplify signals right-to-left. Monitoring, fast failure detection, fix before moving on.
  • 3. Continual learning: a culture of experimentation, blameless post-mortems, repeating practice.
DORA — the four key metricsDevOps Research & Assessment / Accelerate (2018)Measurement
How you prove DevOps is working, with numbers.
  • Deployment frequency — how often you ship (elite = on demand).
  • Lead time for changes — commit to running in production.
  • Change failure rate — % of deploys that cause an incident.
  • Mean time to restore (MTTR) — how fast you recover from failure.
  • Exam move — first two measure velocity, last two measure stability. Good DevOps improves all four together, disproving the old "fast vs safe" trade-off.
MLOpsextends DevOps to ML, ~2018+Core
DevOps plus two new things that change everything: data and models.
  • New artifacts — you must version not only code but the data and the trained model.
  • Reproducibility — same data + code + params must rebuild the same model.
  • Experiment tracking + model registry — tools like MLflow record runs and store approved models.
  • Drift & continuous training — the world changes, so models decay; monitoring triggers retraining.
  • Your project link — you consume models as a managed service (Claude via Bedrock), so you skip the training half of MLOps but still live the serving, monitoring and versioning half.
"DevOps is not a goal, but a never-ending process of continual improvement."Jez Humble · co-author of Continuous Delivery

In your project

How the final project is DevOps

  • Automation — one command (deploy.sh) goes from nothing to a running HTTPS platform.
  • Reproducibility — the CloudFormation template + repo rebuild the identical stack every time.
  • Shared definition — the whole system lives as text in git, readable by anyone.
  • Fast feedback — destroy and recreate in minutes, so experiments are cheap and reversible.

Exam moves

  • Define DevOps as culture first, tools second. Lead with the silo problem.
  • If asked "is DevOps just automation?" say no, cite CALMS and the Three Ways.
  • Name the four DORA metrics and split them into velocity vs stability.
  • Explain MLOps as "DevOps + data + model", and name drift and retraining as the new failure modes.
  • Use the loop diagram to place any tool: a tool automates one or more arrows.
Chapter two · Version control

02Git & GitHub

Version control is the foundation everything else stands on: if it is not in git, it does not exist, cannot be reviewed, and cannot be automated.

Git is a distributed version-control system: every clone holds the full history, so you can commit, branch and diff offline. GitHub is a hosted home for git repositories that adds collaboration on top: pull requests, code review, issues, and automation through GitHub Actions. Git is the engine; GitHub is the shared workshop built around it.

Branch off main, commit in isolation, open a pull request, get it reviewed, then merge back. Main stays clean and releasable.

The concepts worth knowing cold

The pull request workflowCore
The unit of collaboration and the natural place to attach automated checks.
  • Create a branch from main for one change.
  • Commit work, then open a pull request to merge it back.
  • The PR is where review happens and where CI runs automatically (Block 3).
  • Merge only when review approves and checks pass — this is the human + automated quality gate.
Branching strategiesCompare
How teams organise branches to balance safety and speed.
  • GitFlow — long-lived main + develop + feature/release/hotfix branches. Safe, ceremonial, slower.
  • Trunk-based — everyone commits to one trunk via tiny short-lived branches. Fast, needs strong CI and feature flags.
  • Exam move — map strategy to the promotion flow: a merge to main deploys dev, a tag promotes to stage and prod.
Conventional Commits + SemVerDiscipline
Structured commit messages that let machines compute the next version number.
  • Format type(scope): description — feat, fix, docs, chore, with ! for breaking.
  • SemVer — MAJOR.MINOR.PATCH; breaking bumps MAJOR, feat bumps MINOR, fix bumps PATCH.
  • Commitizen reads the commits and bumps the version + writes the changelog automatically.

In your project

GitHub in the LobeChat build

  • The whole stack lives in a fork, with origin = your repo and upstream = the original.
  • The EC2 clones the repo at boot — so the repo is not just storage, it is part of the deploy.
  • Release is tagged final-vX.Y.Z with cz bump (Commitizen + SemVer).
  • Submission = a private repo with the grader invited as a collaborator.

Exam moves

  • Distinguish git (the tool) from GitHub (the hosted platform) in one sentence.
  • Explain why "branch, PR, review, merge" is the safety mechanism, not bureaucracy.
  • Tie Conventional Commits to automated versioning and changelogs.
  • Contrast GitFlow vs trunk-based by speed-vs-safety, then say which fits CI/CD better (trunk-based).
Chapter three · Automation pipeline

03Continuous integration, delivery & deployment

CI/CD is the conveyor belt that turns a commit into running software, with automated gates so speed never costs safety.

The three C's are a ladder. Continuous Integration means every change is merged frequently and automatically built and tested. Continuous Delivery means the result is always in a releasable state, with deployment one button-press away. Continuous Deployment removes even that button: every change that passes the pipeline goes to production automatically.

CI covers source-to-test. The difference between delivery and deployment is a single human approval before production.

The concepts worth knowing cold

Continuous IntegrationCore
Integrate small changes constantly so problems surface in minutes, not at a painful big-bang merge.
  • Every push triggers an automated build + test.
  • A red build blocks the merge — the team keeps main always green.
  • Kills "integration hell" by making integration tiny and frequent.
Delivery vs DeploymentCompare
Both keep prod-ready artifacts; the only difference is who presses go.
  • Continuous Delivery — automated up to production, a human approves the final release. Best when releases need judgement or compliance sign-off.
  • Continuous Deployment — no human gate, every green build ships. Needs very strong tests and monitoring.
  • Exam move — "all deployment is delivery, not all delivery is deployment".
GitHub ActionsTool
CI/CD built into GitHub, triggered by repo events.
  • Workflow — a YAML file in .github/workflows/ triggered by an event (push, PR, tag).
  • Job — runs on a runner (a VM); jobs contain ordered steps.
  • Step — a shell command or a reusable action.
"If it hurts, do it more often, and bring the pain forward."Continuous Delivery principle — Humble & Farley (2010)

In your project

The promotion flow you designed

  • Merge to main → deploys dev; a tagged release candidate → stage; a manual approval + final tag → prod.
  • That manual gate is the textbook line between delivery and deployment.
  • deploy.sh is your deploy stage: it resolves the AMI and IP, validates, then runs CloudFormation.
  • Each environment is the same template as a separate stack — promotion is a parameter change, not a rewrite.

Exam moves

  • Draw the pipeline and label where CI ends and CD begins.
  • State the delivery-vs-deployment difference as "one manual approval".
  • Explain CI's value as "small batches + fast feedback = less risk".
  • Name GitHub Actions vocabulary: workflow, job, runner, step, action.
Chapter four · Provisioning

04Infrastructure as Code

Stop clicking in consoles. Describe the infrastructure you want in a versioned file, and let a tool make reality match the file.

Infrastructure as Code (IaC) manages servers, networks and cloud resources through machine-readable definition files instead of manual setup. Because the infrastructure is now text, it can be reviewed, versioned in git, diffed and rebuilt identically. This kills configuration drift and the "works on the one server nobody dares touch" problem.

Declarative IaC: you state the destination, the engine computes the steps. Running it twice changes nothing the second time — that is idempotency.

The concepts worth knowing cold

Declarative vs imperativeCore
Tell the tool what you want, not how to get there.
  • Declarative — "I want one EC2, one VPC, this security group." The engine figures out the order and the API calls. Re-running converges to the same state.
  • Imperative — "run this, then that." You own the sequencing and the "does it already exist?" checks.
  • Terraform and CloudFormation are declarative; a raw bash script is imperative.
Terraform vs CloudFormationCompare
The two IaC tools in this course, and why your project switched between them.
  • Terraform — works across clouds, uses HCL, and you manage a state file that records what exists.
  • CloudFormation — AWS-native, YAML/JSON templates grouped into stacks, with AWS holding the state for you.
  • Trade-off — Terraform is portable; CloudFormation is deeply integrated with AWS and needs no state backend.
Immutable infrastructurePrinciple
Servers are cattle, not pets: you replace them, you do not nurse them.
  • To change a server, build a new one from the definition and throw the old one away.
  • Eliminates drift and "snowflake" servers nobody can reproduce.
  • Pairs naturally with IaC and containers.
"Infrastructure as Code treats your servers, networks and load balancers the same way developers treat application code: written, reviewed, versioned, tested."Kief Morris · Infrastructure as Code

In your project

From Terraform (v1) to CloudFormation (v2)

  • The teacher required CloudFormation, so v1's Terraform was rewritten as one declarative lobechat.yaml template.
  • One template provisions VPC, subnet, internet gateway, route table, EIP, security group, IAM role, and the EC2 — all as desired state.
  • Promotion uses the same template per environment, parameterised — the IaC dream.
  • Real-world wrinkle — the sandbox blocked the SSM-parameter AMI lookup, so the AMI is resolved at deploy time and passed as a parameter. No hardcoded AMI; the lookup stays dynamic.

Exam moves

  • Define IaC and immediately name its three wins: versioned, reproducible, no drift.
  • Contrast declarative vs imperative with a one-line example each.
  • Compare Terraform vs CloudFormation on portability and state management.
  • Explain idempotency as "running it again changes nothing".
  • Link immutable infrastructure to "cattle not pets".
Chapter five · Containers

05Docker & containers

Package an app with everything it needs into one portable unit, so "it works on my machine" becomes "it works everywhere".

A container bundles an application with its dependencies and runs as an isolated process that shares the host's operating-system kernel. That makes it far lighter than a virtual machine, which carries a whole guest OS. Docker is the tooling to build, ship and run containers, and Docker Compose defines and runs a multi-container application from a single YAML file.

VMs each carry a full guest OS (heavy). Containers share the host kernel (light), so they start in seconds and pack densely.

The concepts worth knowing cold

Image vs containerCore
Blueprint vs the thing built from it — the single most common exam confusion.
  • An image is a read-only, layered blueprint (class). It is built once and shared via a registry.
  • A container is a running instance of an image (object). You can start many from one image.
  • Images are built from a Dockerfile, whose instructions become cached layers.
The DockerfileBuild
A deterministic recipe so anyone rebuilds the exact same image.
  • FROM a base image, RUN install steps, COPY code in, CMD the start command.
  • Each instruction is a cached layer — order them cheap-to-expensive so rebuilds stay fast.
  • This is reproducibility (Block 1) and immutability (Block 4) at the application level.
Docker ComposeOrchestrate (single host)
Declare a multi-service app once, bring it all up with one command.
  • A docker-compose.yml lists every service, its image, ports, volumes, env and dependencies.
  • docker compose up -d starts the whole stack on one host with an internal network so services reach each other by name.
  • For many hosts you graduate to an orchestrator like Kubernetes; Compose is the single-host tool.
"Build once, run anywhere — the container carries its environment with it."The core Docker promise

In your project

Docker is the heart of your stack

  • The entire platform is a 10-service docker-compose.yml — LobeChat, Casdoor, Postgres, MinIO, Qdrant, MCPHub, Hayhooks, LiteLLM, Caddy and more.
  • Services talk over the Compose network by name (LobeChat reaches mcphub:3000, Caddy proxies lobe-chat:3210).
  • Volumes persist Postgres, MinIO and Qdrant data; healthchecks gate start-up order.
  • The boot script installs Docker, then runs docker compose up -d --build — containers are the unit you actually ship.
  • The "no source modifications" rule meant removing a bind-mounted patch — a very concrete Docker volume lesson.

Exam moves

  • Explain container vs VM with the "shared kernel vs full guest OS" diagram.
  • Never confuse image (blueprint) with container (running instance).
  • Describe a Dockerfile as a layered, cached, reproducible recipe.
  • Position Compose as single-host orchestration and Kubernetes as multi-host.
  • Connect containers back to Block 1: they deliver reproducibility and immutability.
Chapter six · Configuration management

06Ansible & configuration management

Once a server exists, something has to install packages, write config files and start services on it, consistently, across one machine or a thousand. That is configuration management, and Ansible is the agentless way to do it.

IaC (Block 4) provisions the empty machine. Configuration management then configures what runs on it. Ansible does this with simple YAML playbooks, connecting over plain SSH with no agent to install on the target. It is push-based and idempotent: describe the desired end state and Ansible only changes what is not already correct.

One control node pushes the desired configuration to many targets over SSH. Nothing special is pre-installed on them — that is what "agentless" means.

The concepts worth knowing cold

Agentless, push, idempotentCore
The three words that define Ansible in an exam.
  • Agentless — no software to install on targets; it rides over SSH (plus Python on the host).
  • Push — the control node initiates and sends configuration out (Chef/Puppet instead pull from a server via an agent).
  • Idempotent — modules check current state and act only if needed, so re-running is safe.
Playbook anatomyBuild
A YAML file that maps hosts to the tasks that bring them to a desired state.
  • Inventory lists the hosts and groups; a playbook targets them.
  • A play binds hosts to tasks; each task calls a module (e.g. install a package, copy a file).
  • Handlers run only when notified by a change (e.g. restart a service after its config changed).
  • Templates (Jinja2) generate config files from variables.
Provisioning vs configuration managementCompare
Two different jobs that work as a relay, not rivals.
  • Provisioning (Terraform / CloudFormation) — create the infrastructure: the VPC, the empty server.
  • Configuration management (Ansible) — set up what runs inside that server: packages, files, services.
  • The clean pipeline is: IaC creates the host, then Ansible configures it, then Docker runs the app.
"Ansible's goal is to be the simplest way to automate: human-readable, agentless, and safe to run again and again."Ansible design philosophy

In your project

Where configuration management lives in your build

  • Your bootstrap.sh does the configuration-management job — installs Docker and the AWS CLI, writes the .env, rewrites Casdoor URLs, brings the stack up.
  • But it does it imperatively in bash. The "textbook" version of that exact work is an Ansible playbook: idempotent tasks instead of a linear script.
  • That contrast is itself an exam answer: same goal, imperative bash vs declarative idempotent Ansible.
  • It also completes the relay: CloudFormation provisions the EC2, the boot script configures it, Docker runs the app.

Exam moves

  • Define Ansible in three words: agentless, push, idempotent.
  • Contrast push (Ansible) vs pull + agent (Chef/Puppet).
  • Separate provisioning (IaC) from configuration management (Ansible) and show how they chain.
  • Name the building blocks: inventory, playbook, play, task, module, handler, role, template.
  • Explain idempotency as the reason a playbook is safe to run repeatedly.
§ Closing · How the toolchain grew up

DevOps across the decades

Each era added a layer your project now uses all at once. Anchoring tools to their moment makes the whole stack make sense.

2000s — Agile spills into operations

  • 2001 — the Agile Manifesto speeds up development, exposing Ops as the new bottleneck.
  • 2009 — Patrick Debois coins "DevOps"; the first DevOpsDays.

2010–2013 — the culture gets a name and a book

  • 2010 — Humble & Farley, Continuous Delivery. CALMS appears.
  • 2013 — The Phoenix Project popularises the Three Ways. Docker launches: containers go mainstream.

2014–2016 — infrastructure becomes code

  • 2014 — Terraform and Kubernetes released; AWS CloudFormation maturing. Ansible rising as agentless config management.

2018–now — measurement and machine learning

  • 2018 — Accelerate formalises the four DORA metrics. MLOps emerges as ML hits production.
  • 2019 — GitHub Actions brings CI/CD into the repo. 2020s — managed LLM APIs (Bedrock) make AI a service you call, the world your project lives in.
