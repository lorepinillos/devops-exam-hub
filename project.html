Chapter one · The system in one breath

01What we built and why

A self-hosted LobeChat AI-chat platform, its whole docker-compose stack running on a single AWS EC2, reachable over HTTPS, provisioned by CloudFormation. That sentence is the spine of the exam.

The point of the project is to deploy something real end to end and understand every moving part. LobeChat is the chat UI, but it only works because a handful of supporting services run alongside it: a database, object storage, a vector store, an SSO provider, a tools hub, an LLM bridge and a reverse proxy. The DevOps value is that the entire system is code (compose file + CloudFormation template + boot script in git), so it is reproducible, reviewable and rebuildable.

The request lifecycle — how a chat message travels

This is the single most testable flow ("how does LobeChat communicate with X"). Trace it:

  1. Browser hits https://<host>; Caddy terminates TLS and proxies to LobeChat.
  2. If not logged in, LobeChat redirects to Casdoor for OAuth sign-in, then back.
  3. You send a message. LobeChat may retrieve context from Qdrant via MCPHub, attach uploaded files from MinIO, and read/write chat history in Postgres.
  4. LobeChat sends an OpenAI-format request to LiteLLM, which translates it to Bedrock and streams Claude's answer back.

The whole stack runs on how many EC2 instances in the deployed (dev) environment?

  2. One instance per service
  3. A Kubernetes cluster of three nodes
  4. Two instances, app and database
Show answer
A. A single EC2 runs the entire docker-compose stack. That is the whole point of the lift-and-shift: one host, many containers.

Exam traps & tips

  • "Deploying something" is the technical part — expect questions on the repo and the deploy, not abstract DevOps trivia.
  • Be able to name all ten services and one sentence of what each does.
  • Know the message lifecycle cold: Caddy → LobeChat → (Casdoor / Postgres / MinIO / MCPHub / Qdrant) → LiteLLM → Bedrock.
Chapter two · Containers

02Docker, Compose & the Dockerfiles

The teacher said it plainly: understand the Dockerfiles. Containers are the unit we ship, and Compose is how the ten of them come up together on one host.

A container packages an app with its dependencies and shares the host kernel, so it is light and portable (unlike a VM, which carries a full guest OS). An image is the read-only blueprint; a container is a running instance of it. A Dockerfile is the recipe that builds an image, layer by layer. Docker Compose describes a multi-container app in one YAML file and starts it all with docker compose up.

Only Caddy publishes ports to the outside (80/443). Everything else is reachable only inside the network, by service name. That is why http://mcphub:3000 works from LobeChat but not from your browser.

The pieces of Compose worth knowing cold

Build vs pull (the Dockerfile question)Understand
Most services use a ready-made image; MCPHub is built locally from a Dockerfile.
  • Most services set image: and pull a published image (e.g. lobehub/lobe-chat-database).
  • MCPHub uses build: against dockerfiles/mcphub.Dockerfile, which extends the base image to add system tools (graphviz, gcc, docker CLI) needed by some stdio MCP servers.
  • Why build? Because the stdio tools need extra binaries that are not in the base image. You bake them in at build time, not by hand-editing a running container.
Volumes, ports, depends_on, healthcheckWiring
The four Compose knobs the exam can poke at.
  • Volumes persist data outside the container so it survives restarts (Postgres, MinIO, Qdrant data live in ./data).
  • Ports map container ports to the host. Only Caddy needs this; the rest stay internal.
  • depends_on + healthcheck control start order so LobeChat does not start before Postgres is healthy.
Likely MCQ · the teacher's Kubernetes question
If we already have Docker (Compose), why would we ever want Kubernetes?
  1. Kubernetes replaces Docker as the container runtime
  2. To orchestrate containers across many hosts with auto-scaling, self-healing and rolling updates
  3. Because Compose cannot run more than one container
  4. Kubernetes is required for HTTPS
Show answer
B. Compose is single-host. Kubernetes orchestrates containers across a cluster of many hosts, adding scaling, self-healing, rolling updates and scheduling. You graduate to it when one machine is no longer enough. It does not replace Docker, it orchestrates containers (often Docker/containerd ones).
Likely MCQ
From your browser, why can you not open http://mcphub:3000 directly?
  1. MCPHub is down
  2. mcphub is an internal Docker-network name, only resolvable between containers; the browser is outside that network
  3. It needs a password
  4. Port 3000 is blocked by Bedrock
Show answer
B. Service names resolve only on the Compose network. The browser reaches services only through Caddy on 443. This is also why the MCP plugin URL inside LobeChat is http://mcphub:3000/mcp/... (a server-side call), not a public URL.

Exam traps & tips

  • Image = blueprint, container = running instance. Never swap them.
  • Container vs VM: shared kernel (light) vs full guest OS (heavy).
  • Only Caddy publishes ports; internal services talk by name. Great trap material.
  • "Why build MCPHub from a Dockerfile?" → it needs extra system binaries baked in.
Chapter three · State

03How LobeChat stores data & talks to services

The teacher flagged this directly: how does LobeChat store data, and how does it communicate? There are three stores, each for a different shape of data.

Relational data in Postgres, files in MinIO, meaning (vectors) in Qdrant. Match the data shape to the store.

Postgres — the source of truthStore
  • One shared Postgres (shared-postgres) holds both the LobeChat database and the Casdoor database (created by init-postgres.sql).
  • LobeChat connects via DATABASE_URL=postgresql://...@postgres:5432/lobechat — again, by service name.
MinIO — S3 for filesStore + classic error
  • MinIO is an S3-compatible object store; LobeChat uploads files to it with the S3 SDK.
  • Why it errored — uploads failed with a browser "Mixed Content" error until S3_ENDPOINT was set equal to S3_PUBLIC_DOMAIN (both the public HTTPS host). LobeChat signs the URL with the endpoint host and hands it to the browser, so an internal http://minio:9000 got blocked.
  • The lobe bucket does not auto-create, so the boot script makes it.
Qdrant — vectors for RAGStore
  • Stores embeddings so the assistant can do semantic retrieval (Retrieval-Augmented Generation).
  • Reached as a tool through MCPHub, not directly by the chat UI.
Likely MCQ
Where does LobeChat store an uploaded PDF?
  1. In PostgreSQL as a blob
  2. In MinIO, the S3-compatible object store
  3. In Qdrant as a vector
  4. On the Caddy container
Show answer
B. Files go to MinIO (object storage). Postgres holds the structured metadata/record, Qdrant holds vector embeddings, never the raw file.

Exam traps & tips

  • Three stores, three data shapes: relational (Postgres) · files (MinIO) · vectors (Qdrant).
  • One Postgres is shared by LobeChat and Casdoor.
  • "Why did file upload fail?" → S3_ENDPOINT must equal S3_PUBLIC_DOMAIN (Mixed Content).
  • Communication is always by service name over the Docker network.
Chapter four · The front door

04Caddy, HTTPS & Casdoor SSO

Why so much fuss about HTTPS and a reverse proxy? Because OAuth login literally breaks without it, and because the exam expects you to know why we reject the raw IP.

Caddy is the reverse proxy and the only service exposed to the internet. It terminates TLS, automatically obtains a Let's Encrypt certificate, and routes each hostname to the right container. Casdoor is the SSO identity provider that handles login via OAuth, so user identity is centralised and every session is attributable.

Why HTTPS is mandatoryWhy
  • OAuth cookies — browsers refuse Secure / cross-site cookies over plain HTTP, so the Casdoor login flow silently fails on HTTP.
  • Confidentiality + integrity — traffic is encrypted, not readable or tamperable in transit.
  • A self-signed cert is not acceptable: browsers warn and OAuth callbacks break. We use a real CA (Let's Encrypt) on a real hostname (nip.io maps the IP to a name a CA will sign).
Why reject the raw IP / direct originWhy
  • Hitting the raw IP over HTTPS fails the TLS handshake (no cert for an IP), and Caddy answers plain HTTP with 421 Misdirected Request.
  • Port 47000 (the app's local dev port) is closed at the security group — only 80/443 are open.
  • This proves traffic must go through the proxy and its hostname, which is exactly what the grading checklist tests.
Casdoor gotchaError
  • The seeded login is org lobechat, user user, password pswd123.
  • Why admin login fails — the admin account only exists in the built-in org, which LobeChat does not use. Wrong org = no login.
Likely MCQ
Why does the Casdoor sign-in flow fail when the site is served over plain HTTP?
  1. Casdoor needs a GPU
  2. Browsers will not send Secure / cross-site OAuth cookies over HTTP, so the session never establishes
  3. HTTP is slower
  4. Bedrock blocks HTTP
Show answer
B. TLS, DNS, OAuth and cookies are coupled. Without HTTPS the Secure/SameSite cookie rules stop the login round-trip, so the redirect loops or errors.

Exam traps & tips

  • Caddy is the only internet-facing service; it does TLS + routing + auto Let's Encrypt.
  • HTTPS is required for OAuth cookies, not just "for security".
  • Raw IP rejected = handshake fails (HTTPS) and 421 (HTTP); only 80/443 open.
  • Casdoor: org lobechat, not built-in.
Chapter five · The intelligence

05LiteLLM, Bedrock, MCP & MCPHub

This block carries most of the teacher's MCP notes: MCPHub avoids a problem, MCP's weakness is stdio, and if an MCP makes you suffer, change it.

LobeChat connects to MCPHub once; MCPHub fans out to ~10 MCP servers. That is the "problem it avoids": wiring every tool into LobeChat individually.

LiteLLM — the vendor-neutral bridgeWhy we use it
  • LobeChat speaks the OpenAI API; Bedrock does not. LiteLLM sits between them and translates, so LobeChat thinks it is talking to OpenAI.
  • Why it matters — switching provider (Bedrock → OpenAI → OpenRouter → local) is a one-file config change. It breaks vendor lock-in.
  • It uses the EC2 instance role for Bedrock auth — no API key in env. (This needs IMDS hop limit = 2 so the container can reach the metadata service.)
  • Classic error — Bedrock Claude rejects requests with both temperature and top_p; fixed by dropping top_p in the LiteLLM config.
MCP & MCPHubTeacher's notes
  • MCP (Model Context Protocol) is the standard for giving a model tools (search, files, databases).
  • MCPHub avoids a problem — it aggregates ~10 MCP servers behind one endpoint, so LobeChat integrates once instead of wiring each tool separately.
  • MCP's weakness is stdio — many servers use the stdio transport, which is fragile: long-lived sessions drop, especially behind a proxy, and it does not survive reconnections well. Streamable-HTTP is sturdier.
  • If an MCP makes you suffer, change the MCP — do not fight a flaky server; swap its transport or replace the server. We saw this with the dropped retry patch.
Likely MCQ · MCP weakness
What is the main practical weakness of MCP in this stack?
  1. It cannot return text
  2. The stdio transport is fragile for long-lived sessions, especially through a proxy
  3. It requires Kubernetes
  4. It only works with OpenAI
Show answer
B. stdio is the weak point. Long-lived stdio sessions drop and reconnect badly behind a reverse proxy, which is why the MCP demo is done early after a fresh boot, and why "if it makes you suffer, change the MCP".
Likely MCQ · why LiteLLM
Why is LiteLLM in the stack at all?
  1. To store chat history
  2. To translate LobeChat's OpenAI-format calls into Bedrock calls and to avoid vendor lock-in
  3. To serve the web UI
  4. To issue TLS certificates
Show answer
B. It is an OpenAI-compatible proxy/bridge to Bedrock, and the single swap point that lets you change LLM provider with a config edit.

Exam traps & tips

  • MCPHub's value = one integration point for many tools (avoids wiring each).
  • MCP weakness = stdio (fragile sessions). Streamable-HTTP is more robust.
  • "If the MCP makes you suffer, change the MCP" — swap transport/server, do not patch around it.
  • LiteLLM = OpenAI→Bedrock bridge + anti-lock-in; uses instance role (hop limit 2).
  • Bedrock error trap: temperature + top_p together is rejected.
Chapter six · Provision, configure, ship

06IaC, Ansible, GitHub & secrets

How the host comes into being, how it gets configured, and the rules about secrets and source code the teacher called out.

The relay: IaC creates the empty machine, configuration management sets it up, Docker runs the app. Three jobs, three tools.

IaC — CloudFormation (and the Terraform story)Provision
  • One declarative CloudFormation YAML provisions the VPC, subnet, internet gateway, route table, Elastic IP, security group, IAM role and the EC2. AWS holds the state; you deploy a stack.
  • v1 used Terraform; the teacher required CloudFormation, so v2 is a clean rewrite. Same resources, different tool.
  • Deviations to know — the AMI is resolved at deploy time via ec2:DescribeImages and passed as a parameter (the sandbox blocks the SSM-parameter route), and secrets live in .env on the encrypted EBS volume (the sandbox blocks SSM and Secrets Manager).
Why do we need Ansible?Teacher's note
  • To deploy and set up software on a machine: install packages, write config files, start services. That is configuration management.
  • It is agentless (just SSH), push-based and idempotent (safe to re-run).
  • In our project the bootstrap.sh does this job imperatively in bash; Ansible would do the same work declaratively with idempotent tasks. Provisioning (CloudFormation) makes the box, Ansible configures it.
Secrets: .env vs GitHub Secrets · and never modify sourceRules
  • .env holds secrets at runtime on the host; it is gitignored and never committed. Ours is generated at boot.
  • GitHub Secrets store credentials for CI/CD (GitHub Actions) so workflows authenticate without secrets in the repo.
  • Modifying the source code is bad practice — it breaks upgrades and reproducibility. We deploy the app as shipped and configure from outside (this is why the route.js patch was removed).
GitHub Actions — could be asked to write oneBe ready
A minimal workflow that validates the CloudFormation template on every push.
name: validate
on: [push]
jobs:
  cfn-lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install cfn-lint
      - run: cfn-lint cloudformation/lobechat.yaml
  • Trigger (on: push) → job on a runner (ubuntu-latest) → ordered steps (checkout, install, lint).
  • Recognise the shape: this is CI for infrastructure code.
Likely MCQ
Why is editing LobeChat's shipped source code to fix a bug considered bad practice here?
  1. It is illegal
  2. It breaks reproducibility and upgrades; you should configure from outside, not fork the source
  3. It makes the container smaller
  4. It is required by Kubernetes
Show answer
B. Patching shipped code means every upgrade re-breaks, and the deployment is no longer reproducible from the official image. Configure via env/compose/proxy instead. This is exactly why the v2 build removed the bind-mounted route.js patch.

Exam traps & tips

  • Ansible answer = "deploy and set up software" (configuration management), agentless + idempotent.
  • Provision (CloudFormation) ≠ configure (Ansible) ≠ run (Docker). Know the relay.
  • Secrets never in git: .env (runtime, gitignored) vs GitHub Secrets (CI/CD).
  • Do not modify shipped source; configure from outside.
  • Be able to sketch a GitHub Actions workflow: on → jobs → runner → steps.
  • CloudFormation is declarative and AWS-native; v1 Terraform was swapped for it.
§ Closing · rapid-fire

Exam-day Q&A bank

The questions the teacher hinted at, with crisp answers. Click to reveal and self-test.

Why do we need Ansible?
To deploy and set up software on a server: install packages, write config files, start services. It is configuration management — agentless (SSH), push-based, idempotent. Provisioning (CloudFormation) makes the machine; Ansible configures it.
What problem does MCPHub solve?
It aggregates many MCP servers behind one endpoint, so LobeChat integrates once instead of wiring each tool (qdrant, filesystem, aws-docs, …) individually.
What is MCP's main weakness?
stdio as a transport. Long-lived stdio sessions are fragile and drop, especially behind a reverse proxy. Streamable-HTTP is more robust.
An MCP server keeps failing. What do you do?
Change the MCP — swap its transport (stdio → streamable-http) or replace the server. Do not fight it or hack patches around it.
Where do secrets go: .env or GitHub Secrets?
Both, for different jobs. .env holds runtime secrets on the host and is gitignored (never committed). GitHub Secrets hold credentials for CI/CD workflows so nothing sensitive sits in the repo.
Why is modifying the source code bad practice?
It breaks reproducibility and upgrades: every new image re-breaks your patch, and the deploy is no longer rebuildable from the official artifact. Configure from outside (env, compose, proxy). This is why the route.js patch was removed in v2.
If we have Docker, why would we want Kubernetes?
Docker Compose is single-host. Kubernetes orchestrates containers across a cluster of many hosts, adding auto-scaling, self-healing, rolling updates and scheduling. You move to it when one machine is no longer enough. It does not replace the container runtime, it orchestrates containers.
How does LobeChat store data?
Three stores by data shape: PostgreSQL for structured data (chats, users, settings, plus Casdoor's data), MinIO (S3) for uploaded files, and Qdrant for vector embeddings used in RAG.
How does LobeChat communicate with the model?
It sends OpenAI-format requests to LiteLLM, which translates them to AWS Bedrock and streams Claude's response back. LiteLLM authenticates to Bedrock with the EC2 instance role.
Why must the site be HTTPS, not HTTP?
OAuth login needs Secure cross-site cookies, which browsers refuse over HTTP, so Casdoor sign-in fails. HTTPS also gives confidentiality and integrity. Self-signed certs are rejected, so we use Let's Encrypt on a real hostname.
Why do we reject the raw IP / direct origin?
Traffic must go through the proxy hostname. Raw-IP HTTPS fails the handshake (no cert for an IP) and raw-IP HTTP returns 421 Misdirected Request; only 80/443 are open at the security group. The graders test this explicitly.
Why CloudFormation instead of clicking in the AWS console?
Infrastructure as Code: the stack is versioned, reviewable, reproducible and free of configuration drift. One template rebuilds the identical environment every time, and tears it down cleanly.
Why is LiteLLM there, and why does it prevent lock-in?
LobeChat speaks OpenAI; Bedrock does not. LiteLLM bridges them, and it is the single config file where you can re-point to OpenAI, OpenRouter or a local model — so the exit cost from any provider is a YAML edit.
Classic errors: name three and their cause.
Mixed Content on upload → S3_ENDPOINT not equal to S3_PUBLIC_DOMAIN. "Model use case details not submitted" → Bedrock Anthropic console form not filled. "temperature and top_p cannot both be specified" → drop top_p in LiteLLM. (Bonus: container can't reach Bedrock → IMDS hop limit must be 2.)
