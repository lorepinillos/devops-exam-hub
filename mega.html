§ the story · how the solution grew up

From "it runs" to a cloud product

The repo's branches are the homework build-up. Each stage adds exactly one DevOps pillar, and the solution gets more professional step by step. Read it top to bottom for the global picture, then dive into the chapters.

v1.x

Just run the app

Containers

Lift-and-shift LobeChat locally with Docker Compose. Installation instructions, nothing else.

ProIt works — the fastest path to a running chat platform.
ConManual, single host, no automation, no tests, no cloud, not reproducibly deployable.

Why move on: a working app you cannot reliably reproduce, test or deploy is not engineering yet.

v2.x

Add Continuous Integration

CI · GitHub Actions

A first GitHub Actions workflow: clone LobeChat, run a type-check (~1 min) and ESLint (~2 min), manual workflow_dispatch trigger, 15-minute timeout.

ProFirst automation — quality checks run automatically, errors caught early.
ConOnly checks code; it does not build or deploy anything, and there is still no cloud infrastructure.

Why move on: checking code is good, but the environment it runs in is still hand-built and unreproducible.

v3.x

Infrastructure as Code

IaC · CloudFormation

An infra/cloudformation.yml describing VPC, EC2, PostgreSQL, MinIO and LobeChat, plus (briefly) a deploy workflow, later simplified to a manual CloudFormation deploy with an architecture diagram.

ProThe cloud environment is now versioned code, reproducible, no console clicking, drift eliminated.
ConSetup is baked into the EC2 UserData — provisioning and configuration are tangled in one script.

Why move on: mixing "create the server" and "configure the server" in one blob does not scale or stay clean.

v4.x

Separate provisioning from configuration

Config mgmt · Ansible

Replace the UserData script with an Ansible playbook (Postgres, MinIO, Node.js, LobeChat). CloudFormation becomes infrastructure-only. Two phases: CloudFormation provisions, then Ansible configures over SSH. Commitizen added.

ProClean separation of concerns; idempotent, declarative configuration; the professional two-phase shape.
ConMore moving parts — inventory, SSH access, playbooks to maintain.

Why move on: with the deploy mechanics solid, the project needs disciplined releases and real features.

v5.x

Release discipline

Versioning · SemVer

Commitizen + semantic-version tags; version bumps (5.0.1 → 5.0.2) with no functional change — purely tightening the release process.

ProPredictable versions and automated changelogs; professional release hygiene and traceability.
ConPure process — adds no new capability by itself.

Why move on: with process and pipeline in place, build out the actual product depth.

main

The full AI platform

Feature depth

The rich stack: Qdrant + Hayhooks RAG, ~12 MCP servers behind MCPHub (with a custom Dockerfile for stdio deps), local vLLM serving Gemma 4 with native function calling, screenshot agent, DB migrations.

ProA genuinely full-featured self-hosted AI platform: tools, retrieval, agents.
ConHeavy and GPU-dependent (local vLLM), many fragile stdio MCP servers, high complexity.

Why move on: to be examined and run cheaply on AWS, the GPU dependency and local assumptions had to go.

lobechat-aws-cfn

Cloud-production rewrite (our build)

Production deploy

A clean CloudFormation rewrite. Bedrock (Claude) via LiteLLM replaces local vLLM (no GPU). HTTPS via Caddy + Let's Encrypt. No source modifications. Secrets handled at boot. One-command deploy.sh.

ProNo GPU, vendor-flexible (swap models in one file), reproducible one-command deploy, HTTPS + SSO, complies with the teacher's rules.
ConSandbox deviations (AMI via DescribeImages, secrets on EBS) and a deliberately single-AZ, cost-optimised footprint.

The destination: ship the platform to AWS professionally, cloud-native, within real constraints.

The arc in one line: App → CI → IaC → Configuration management → Release discipline → Features → Cloud production. Each homework bolts on one pillar, and that sequence is exactly the order of the theory blocks. If an exam question asks "why was X added", the honest answer is almost always "to fix the limitation the previous stage left behind".

Build vs pull — only MCPHub is built

Why the one custom Dockerfile exists.
  • Nine services pull a published image; only mcphub uses build:.
  • Its Dockerfile adds graphviz, libgraphviz-dev, gcc, docker.io on top of samanhappy/mcphub:latest — stdio MCP servers (diagrams, d2) need those binaries, and docker.io lets it spawn container-in-container tools.
  • It also bind-mounts /var/run/docker.sock so it can launch sibling containers (d2, linux-sandbox).
Trap · the :latest contradiction
The midterm's "best practice" answer is avoid :latest (pin versions). Yet this real stack uses :latest for lobe-chat, qdrant, minio and main-latest for litellm. Both can be true: the MCQ wants the principle (pin for reproducibility), while the repo made a pragmatic dev choice. If asked "best practice", answer pin; if asked "what does the repo do", answer it floats on latest.
Trap · depends_on is not "wait until ready"
depends_on with condition: service_started only waits for the container to start, not to be usable. Only service_healthy waits for the healthcheck. LobeChat waits for postgres & minio healthy but casdoor & litellm only started.
Likely MCQ
Which is the ONLY service that publishes ports to the host?
  1. LobeChat
  2. Caddy
  3. MinIO
  4. All of them
Answer
B. Only Caddy maps 80/443 to the host. Everything else is reachable only on the internal Docker bridge by service name — which is the whole point of forcing traffic through the proxy.
Likely MCQ · the Kubernetes question
We already use Docker Compose. Why might we move to Kubernetes?
  1. Compose cannot run more than one container
  2. To orchestrate containers across many hosts with scaling, self-healing and rolling updates
  3. Kubernetes replaces the Docker runtime
  4. HTTPS requires it
Answer
B. Compose is single-host. Kubernetes is multi-host orchestration. It does not replace Docker; it schedules containers across a cluster.
Chapter three · state, precisely

03Postgres, MinIO, Qdrant — and the pgvector trap

Three stores, and one beautiful trap about which one actually does the vector search.

PostgreSQL — operational data (and a decoy vector engine)

  • Image is pgvector/pgvector:pg16 and init-postgres.sql creates databases lobechat and casdoor, then runs CREATE EXTENSION vector in lobechat.
  • The trap: pgvector is installed but not used for the RAG path. Qdrant does the embedding search. Postgres holds users, sessions, messages, agent configs — and Casdoor's data.
  • One shared Postgres named shared-postgres serves both LobeChat and Casdoor.

MinIO — S3 for files

  • API :9000, console :9001, MINIO_REGION_NAME=us-east-1 (S3 SDKs expect a region), CORS allowed only from the LobeChat host.
  • Path-style addressing (S3_ENABLE_PATH_STYLE=1) because MinIO does not do virtual-host buckets like real S3.
  • Healthcheck is mc ready local. The lobe bucket is created by the boot script (it does not auto-create).

Qdrant — the actual vector DB

  • :6333 REST, :6334 gRPC; data in a volume; collection rag-demo.
  • RAG flow: docs → chunk → embed → store; query → embed → nearest-neighbour → top-k → inject into prompt.
  • Reached via qdrant-mcp through MCPHub, never directly from the chat UI.
Trap · who stores the PDF vs who searches it
The raw PDF lives in MinIO. Its chunk embeddings live in Qdrant. Its metadata/ownership lives in Postgres. Three different stores for one upload.
Likely MCQ
Postgres here is the pgvector image. What does the stack use for RAG vector search?
  1. pgvector inside Postgres
  2. Qdrant (a dedicated vector database)
  3. MinIO
  4. Redis
Answer
B. Despite pgvector being available, the RAG path uses Qdrant. Separation of concerns: transactional data in Postgres, embedding search in Qdrant.
Likely MCQ
If Postgres crashes, what happens?
  1. Nothing, it is only for vectors
  2. Login, chat history, agent config and message persistence fail — and Casdoor breaks too
  3. Only file uploads fail
  4. Caddy stops serving TLS
Answer
B. Postgres is the source of truth for LobeChat and Casdoor both. Cached UI may load, but anything stateful dies.
Chapter four · the front door

04Caddy, HTTPS & Casdoor

Why HTTPS is non-negotiable, why the raw IP is rejected, and the org trap that fails your login.

Caddy

  • caddy:2-alpine, the only public service. Terminates TLS, auto-obtains a Let's Encrypt cert per hostname via HTTP-01, routes by host.
  • Three sibling hostnames on nip.io: <ip>.nip.io (LobeChat), auth-<ip>.nip.io (Casdoor), s3-<ip>.nip.io (MinIO). nip.io maps any dashed-IP name to that IP, so a CA will sign it.
  • A request to the raw IP over HTTP gets 421 Misdirected Request; over HTTPS the handshake fails (no cert for an IP).

Casdoor

  • casbin/casdoor:v2.13.0, an OIDC/OAuth2/SAML identity provider, :8000, started with --createDatabase=true; config in casdoor-app.conf (httpport 8000, origin rewritten to the auth hostname at boot).
  • Seeded login: org lobechat, user user, password pswd123.
Trap · why HTTPS, really
Not "for security" in the abstract — OAuth/SSO cookies. Browsers refuse Secure/cross-site cookies over plain HTTP, so the Casdoor login round-trip silently fails. Self-signed certs are also rejected (warnings + broken callbacks). TLS, DNS, OAuth and cookies are coupled.
Trap · the admin login that fails
The admin account exists only in Casdoor's built-in org. LobeChat uses the lobechat org. Logging in as admin fails; you must use user/pswd123 in the lobechat org.
Likely MCQ
Why is the public site served over HTTPS rather than HTTP?
  1. HTTP is deprecated by Docker
  2. OAuth/SSO needs Secure cross-site cookies that browsers refuse over HTTP, so login fails without TLS
  3. HTTPS is faster
  4. Bedrock requires it
Answer
B. The Casdoor login flow breaks on HTTP because of cookie rules. That is the concrete reason, beyond general confidentiality.
Chapter five · intelligence & tools

05LiteLLM, Bedrock, MCP & MCPHub

The densest trap field: model IDs, the function-calling decision, the aggregator, and stdio.

LiteLLM — the OpenAI→Bedrock bridge

  • Exact model map: claude-haiku-4-5 → bedrock/eu.anthropic.claude-haiku-4-5-20251001-v1:0; sonnet-4-5/4-6 similar; titan-embed → bedrock/amazon.titan-embed-text-v2:0.
  • master_key: os.environ/LITELLM_MASTER_KEY (literal string, resolved from env). LobeChat sends that key as its "OpenAI API key".
  • additional_drop_params: ["top_p"] per Claude model — Bedrock Claude rejects requests with both temperature AND top_p.
  • Auth to Bedrock via the EC2 instance role (no key in env) — which needs the IMDS hop limit raised to 2 (Chapter 6).
  • Why it exists / anti lock-in: swapping provider is a one-file config edit; LobeChat is unaware.

The LLM decides to call a tool; LobeChat routes the call to MCPHub; MCPHub dispatches to the right server. MCPHub never talks to the LLM.

MCP & MCPHub — the exact facts

  • The LLM decides when to call a tool (function calling). MCPHub only executes after the model emits a tool_call. Order: prompt → LLM → (maybe) tool → LLM → answer.
  • Standard MCP = one client ↔ one server. MCPHub = aggregator/proxy mounting ~12 servers behind one endpoint, so LobeChat connects once instead of supervising N stdio processes.
  • Servers (12): ssh-exec, notion-mcp, aws-resources-operations, filesystem, playwright, minio-mcp, d2, infrastructure-diagrams, qdrant-mcp, haystack-mcp, linux-sandbox, aws-documentation.
  • Transport: all are stdio except haystack-mcp streamable-http. stdio is MCP's weakness — fragile long-lived sessions, especially through a proxy. "If the MCP makes you suffer, change the MCP" → swap transport/server.

Hayhooks appears twice — one backend, two interfaces

  • REST :1416 (FastAPI + Swagger) for human/API clients; MCP :1417 (hayhooks mcp run --json-response) for MCPHub → LobeChat.
  • Same Haystack pipelines (retriever → … → generator), exposed two ways. The MCP instance pip-installs hayhooks[mcp]==1.1.0 at container start.
Trap · MCPHub does NOT talk to the model
A favourite distractor: "MCPHub sends instructions to vLLM/Bedrock." False. MCPHub is a tool execution layer. The model emits the call, LobeChat routes it to MCPHub, the result returns to the model as a tool message.
Likely MCQ
What is MCP's main practical weakness in this stack?
  1. It cannot return text
  2. The stdio transport is fragile for long-lived sessions, especially through a proxy
  3. It needs a GPU
  4. It only works with OpenAI
Answer
B. stdio. 11 of 12 servers use it, and dropped sessions behind the proxy are why the MCP demo is fired early and why "change the MCP" is the advice.
Likely MCQ · why drop top_p
Why does litellm-config.yaml set additional_drop_params: ["top_p"]?
  1. top_p slows inference
  2. Bedrock-hosted Claude rejects requests that set BOTH temperature and top_p; LobeChat sends both, so top_p is stripped
  3. It saves tokens
  4. top_p is not supported by LiteLLM
Answer
B. "temperature and top_p cannot both be specified" — dropping top_p leaves only temperature, which Bedrock accepts.
Chapter six · provision, configure, ship

06CloudFormation, Ansible, GitHub & secrets

The deploy mechanics, the two sandbox deviations, and the secrets/source rules.

CloudFormation — what the template actually declares

  • Resources: VPC, subnet, internet gateway + attachment, route table + route, security group (22 from your IP, 80/443 public), EIP + association, IAM role + instance profile, the EC2.
  • AmiId is a parameter resolved at deploy time by deploy.sh via ec2 describe-images (the SSM public-parameter route is denied in the sandbox).
  • MetadataOptions: HttpTokens: required (IMDSv2) and HttpPutResponseHopLimit: 2 — the 2 lets containers reach the instance metadata for the role.
  • Root volume gp3, 60 GB, Encrypted: true. Deploy needs CAPABILITY_NAMED_IAM (named role).
  • IAM bedrock-invoke policy: bedrock:InvokeModel + InvokeModelWithResponseStream on the account's inference-profiles and on foundation models anthropic.* + amazon.titan-embed-*.

Why do we need Ansible? (teacher's note)

  • To deploy and set up software on the machine — configuration management. Agentless (SSH + Python), push-based, idempotent.
  • In our project bootstrap.sh does this imperatively in bash; Ansible would do it declaratively with idempotent modules.
  • The relay: CloudFormation provisions the host → Ansible (or the boot script) configures it → Docker runs the app. Correct CI/CD order: build & push image → provision with CloudFormation → generate inventory from stack outputs → run Ansible.

Secrets & source code rules

  • .env = runtime secrets on the host, gitignored, generated at boot. GitHub Secrets = credentials for Actions via ${{ secrets.NAME }}. Never commit secrets to the repo or the workflow YAML.
  • Modifying shipped source is bad practice — breaks reproducibility and upgrades. We configure from outside; the v1 route.js patch was removed in v2.
  • Sandbox deviation: SSM and secretsmanager:CreateSecret are denied, so secrets live in /opt/lobechat/.env (root, 0600) on the encrypted EBS volume. Documented, not ideal.
Trap · provisioning ≠ configuration
CloudFormation/Terraform provision (create the VPC, the empty EC2). Ansible configures (install packages, write files, start services). Docker runs the app. A question that asks "which tool installs software on the server" is Ansible, not CloudFormation.
Likely MCQ · order of operations
Correct order in a CI/CD pipeline combining CloudFormation and Ansible?
  1. Run Ansible → create stack → build image → verify
  2. Build & push image → provision with CloudFormation → generate inventory from outputs → run Ansible
  3. Create stack → build image → delete stack → run Ansible
  4. Generate inventory → run Ansible → build image → create stack
Answer
B. You must provision before you can configure; the inventory (which hosts to configure) comes from the stack's outputs.
Likely MCQ · IMDS hop limit
Why is HttpPutResponseHopLimit set to 2 on the instance?
  1. For faster networking
  2. So containers (one network hop away from the host) can reach the instance metadata service to get the IAM role credentials
  3. To enable HTTPS
  4. To allow two SSH sessions
Answer
B. Default hop limit 1 blocks containers from IMDS. Raising it to 2 lets LiteLLM/MCPHub pick up the instance-role credentials for Bedrock/AWS calls.

§ appendix B · rapid-fire

Exam Q&A bank

Click to reveal. Covers the teacher's hints plus the deep details.

Why do we need Ansible?
To deploy and set up software on a server (configuration management): install packages, write config, start services. Agentless (SSH), push-based, idempotent. Provisioning makes the box; Ansible configures it.
What problem does MCPHub solve?
It aggregates ~12 MCP servers behind one endpoint, so LobeChat integrates once instead of supervising N separate stdio connections.
MCP's weakness?
stdio transport — fragile long-lived sessions, worse through a proxy. 11 of 12 servers use it; only haystack-mcp is streamable-http.
An MCP keeps failing — what do you do?
Change the MCP: swap stdio → streamable-http, or replace the server. Do not patch around it.
Does MCPHub talk to the LLM?
No. The LLM emits a tool call, LobeChat routes it to MCPHub, MCPHub executes and returns the result. MCPHub is a tool execution layer, not an LLM client.
What decides whether a tool is used?
The LLM, via function calling. If the prompt needs external data/side effects it emits a tool_call; otherwise it answers in plain text.
Why does MCPHub need a custom Dockerfile?
Stdio servers need extra binaries (graphviz, libgraphviz-dev, gcc) and docker.io to spawn container-in-container tools. It extends samanhappy/mcphub:latest.
Why is Hayhooks listed twice?
Same Haystack pipelines, two transports: REST :1416 (Swagger) and MCP :1417 (consumed by MCPHub).
Postgres is pgvector — so what does RAG use?
Qdrant. pgvector is present but unused for RAG. Postgres holds operational + Casdoor data.
How does LobeChat store data?
Postgres (structured + auth), MinIO/S3 (files), Qdrant (vectors). Three shapes, three stores.
How does LobeChat reach the model (AWS deploy)?
OpenAI-format request → LiteLLM (:4000) → Bedrock (Claude), streamed back. LiteLLM auth via the EC2 instance role.
Why HTTPS, not HTTP?
OAuth cookies must be Secure/cross-site, which browsers refuse over HTTP, so Casdoor login fails. Plus confidentiality. Self-signed is rejected.
Why reject the raw IP / direct origin?
Traffic must go through the proxy hostname. Raw-IP HTTPS = handshake fail; HTTP = 421; only 80/443 open.
If we have Docker, why Kubernetes?
Compose is single-host. Kubernetes orchestrates across a cluster: scaling, self-healing, rolling updates. It does not replace the container runtime.
Why CloudFormation over the console?
IaC: versioned, reviewable, reproducible, drift-free. One template rebuilds the identical environment and tears it down cleanly.
.env vs GitHub Secrets?
.env = runtime secrets on the host, gitignored. GitHub Secrets = credentials for CI/CD workflows via ${{ secrets.NAME }}. Never commit secrets.
Why not modify the shipped source?
It breaks reproducibility and upgrades. Configure from outside (env, compose, proxy). The v1 route.js patch was removed for this reason.
Why is the LLM container before MCPHub in the flow?
The model must first decide whether to call a tool (inference). MCPHub only executes after that decision.
